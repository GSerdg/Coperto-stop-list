1. Задача
Стоп-лист — список позиций меню, которые сейчас нельзя продать: закончились продукты, сломалось
оборудование, позиция снята до конца смены. Нужно собрать один экран, на котором менеджер зала видит
меню смены, фильтрует его и ставит позиции в стоп-лист или снимает их со стопа. Бэкенд имитируем route
handler'ами Next.js — данные живут в памяти процесса.
Что нужно реализовать
Часть фичи Требования
Список позиций1215 позиций из сид-файла: название, цех (кухня / бар / кондитерская), остаток в
штуках, статус (в продаже / в стоп-листе), причина и срок стопа. Данные приходят из
GET /api/menu-items  с искусственной задержкой. Обязательны состояния загрузки,
ошибки и пустого результата.
ФильтрыДва фильтра: по цеху и по статусу. Состояние фильтров живёт в URL ?
shop=bar&status=stopped ), переживает перезагрузку страницы и корректно работает
с кнопкой «назад». Поиск, сортировка и пагинация не нужны.
Постановка и снятие Панель или модалка с формой: причина (селект из 4 значений) и срок — «до конца
смены» либо конкретное время. Отправка в POST /api/menu-items/:id/stop .
Снятие со стопа — POST /api/menu-items/:id/resume , без отдельной формы.
Оптимистичное
обновление
Позиция меняет статус сразу, не дожидаясь ответа. Сервер отвечает с задержкой 600
мс и примерно в 20 % случаев возвращает ошибку: тогда состояние откатывается к
прежнему, а пользователь видит уведомление об ошибке.

Пример переиспользуемой логики — features/stop-list/model/use-stop-item.ts
import { useMutation, useQueryClient } from '@tanstack/react-query';
import { menuKeys } from './queries';
import type { MenuItem, StopItemPayload } from '@/types/menu';
export function useStopItem(filtersKey: unknown) {
  const qc = useQueryClient();
  const listKey = menuKeys.list(filtersKey);
  return useMutation({
    mutationFn: (vars: { id: string; payload: StopItemPayload }) =>
      stopMenuItem(vars.id, vars.payload),
    onMutate: async ({ id, payload }) => {
      await qc.cancelQueries({ queryKey: listKey });
      const prev = qc.getQueryData<MenuItem[]>(listKey);
      qc.setQueryData<MenuItem[]>(listKey, (items = []) =>
        items.map((item) =>
          item.id === id
            ? { ...item, status: { kind: 'stopped', ...payload } }
            : item,
        ),
      );
      return { prev }; // контекст для отката
    },
    onError: (_err, _vars, ctx) => {
      if (ctx?.prev) qc.setQueryData(listKey, ctx.prev);
    },
    onSettled: () => qc.invalidateQueries({ queryKey: listKey }),
  });
}

3. Валидация и правила стоп-листа
Правила проверяются в двух местах: на клиенте — при потере фокуса поля и при отправке формы, на сервере
— в route handler'е перед изменением данных. Ошибки показываются под полем, отправка при невалидной
форме блокируется.
Поле / сущность Правило
Причина стопа Обязательна. Только одно из четырёх значений StopReason . Пустое значение
селекта не отправляется.
Срок стопа Либо «до конца смены» (until: null ), либо конкретное время. Конкретное время —
строго в будущем, не позже чем через 24 часа, шаг 15 минут.
ОстатокПри остатке 0 позиция не может быть снята со стопа: кнопка «Вернуть в продажу»
заблокирована с подсказкой.
Повторная постановка Позиция, уже находящаяся в стоп-листе, не ставится в стоп повторно — вместо этого
форма открывается в режиме редактирования причины и срока.
Пример: как проверить срок стопа
const MAX_AHEAD_MS = 24 * 60 * 60 * 1000;
const STEP_MS = 15 * 60 * 1000;
export function validateUntil(value: string | null, now = Date.now()): string | null {
  if (value === null) return null;              // до конца смены — всегда валидно
  const ts = Date.parse(value);
  if (Number.isNaN(ts)) return 'Некорректное время';
  if (ts <= now) return 'Время должно быть в будущем';
  if (ts - now > MAX_AHEAD_MS) return 'Не больше чем на 24 часа вперёд';
  if (ts % STEP_MS !== 0) return 'Шаг — 15 минут';
  return null;
}
